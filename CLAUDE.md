# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev`: Vite dev server with HMR
- `npm run build`: type-check (`tsc -b`, project references in `tsconfig.app.json` / `tsconfig.node.json`), then `vite build` to `dist/`
- `npm run lint`: ESLint flat config (typescript-eslint recommended, react-hooks, react-refresh)
- `npm run preview`: serve the production build
- `npm run format` / `npm run format:check`: Prettier (`.prettierrc.json`: single quotes, no semicolons, width 120, trailing commas). Markdown is ignored (`.prettierignore`)

There is no test framework configured yet.

## Stack

React 19 + TypeScript + Vite SPA styled with Tailwind CSS v4, with Supabase as the backend (auth + Postgres), react-router-dom v7 for routing, and zod for form validation. It has no backend code of its own. All data access goes through the Supabase JS client from the browser, so data security depends on Supabase Row Level Security policies, not on client code.

## Architecture

- **Supabase client** (`src/lib/supabase.ts`): a single shared client built from `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` (set in `.env` / `.env.local`, both gitignored). Import this client everywhere. Don't create new clients.
- **Auth state**: `src/context/auth.ts` holds the context and the `useAuth()` hook, and `src/context/AuthContext.tsx` holds only the `AuthProvider` component (split so the `react-refresh/only-export-components` lint rule passes). `AuthProvider` loads the initial session with `getSession()`, then subscribes to `onAuthStateChange`. `useAuth()` returns `{ session, loading }`.
- **Routing** (`src/App.tsx`): `BrowserRouter` wraps `AuthProvider`, which wraps the routes. Private pages are wrapped in `ProtectedRoute` (`src/dashboard/auth`), which shows `ui/PageLoader` while `loading` is true and redirects to `/login` with `state.from` when there is no session; `Login` returns to that `/dashboard…` path after signing in. Public routes (`/`, `/avisos-remates` (old `/remates` redirects there), `/audiencias`, `/pqrs`, `/encuesta`, `/tutoriales`, `/contacto`, and `/login`, login only: accounts are not created from the public site) are nested under `src/layouts/PublicLayout.tsx` (`Header` + `<Outlet />` in `<main>` + `Footer`). Put new public pages inside that layout route. `/login` sits in a second route group with `<PublicLayout footer={false} />`: same header, no footer. Any other path hits `<Route path="*" element={<NotFound />} />` inside the public layout (see "Not found page"). `/dashboard/*` is outside the layout and lazy-loaded from `src/dashboard` (see "Dashboard"). Public nav links are in `mainLinks` in `src/components/navigation/links.ts`. Header uses it. The Footer (`src/components/layout/Footer.tsx`) has its own `services` list, the office contact details, and a row "Publicaciones de los juzgados" with external links built from `src/lib/courts.ts`, one below the other. Its first row also has an "Enlaces de interés" column next to "Servicios" (OECCB spans the row on `sm`, three columns from `lg`). Behind it, `FooterGlow` draws a light moving right to left (see below). The full desktop menu appears only from `xl` up (MainNav, Header and MobileMenu use `xl:`), because the links don't fit on narrower screens. Below that, the hamburger menu is used.
- **Data**: the dashboard's `ProfileProvider` reads the `profiles` table (`id` = auth user id, `full_name`) using `.maybeSingle()`. A missing profile row is expected and is not treated as an error.

## Conventions

- UI text and user-facing messages are in Spanish.
- Format with Prettier, not with the Deno formatter: `.vscode/settings.json` sets Prettier as default formatter; Deno is only the language server for `supabase/functions`.
- TS config is strict about unused locals/params and uses `verbatimModuleSyntax`, so use `import type` for type-only imports.
- Styling uses Tailwind CSS v4 through the `@tailwindcss/vite` plugin. It has no `tailwind.config.js`: add any config in CSS in `src/index.css` (`@theme`, `@layer base`). Use utility classes in `className` rather than inline `style` props or new CSS files. Dark mode uses the `dark:` variant, which follows the system setting.

## Components

`src/components/` has three folders, each with an `index.ts` barrel (import like `import { Button, Card } from '../components/ui'`):
- `ui/`: Button (plus `ButtonLink`, a react-router `Link` styled as a button, and `ButtonAnchor`, an `<a>` for external links: `external` opens a new tab with `noopener`), Input, Select, Badge, Card (plus `CardHeader`/`CardBody`/`CardFooter`), Modal (native `<dialog>`), Alert, Spinner, EmptyState, Pagination, Tooltip (CSS-only caption below an element on hover or keyboard focus; it is `aria-hidden`, so the wrapped element needs its own `aria-label`; `align="end"` right-aligns it for controls near the right edge), PageLoader (full-screen spinner). Button sizes include `icon` (40 px square). Styling variants are `variant`/`size` props backed by class maps inside each file. Input and Select share classes from `ui/styles.ts`.
- `layout/`: Header, Footer, Container (the site-wide `max-w-6xl` + responsive gutters), PageHeader (title, description, optional breadcrumb, actions).
- `navigation/`: MainNav (desktop), MobileMenu (its toggle button lives in Header), Breadcrumb.
- Feature folders (e.g. `pqrs/`) hold a page's own components and data.

## PQRS

`/pqrs` has a 3-step form, `components/pqrs/PqrsForm.tsx`: type → name and email → summary + Cloudflare Turnstile.
- `schema.ts` holds the zod schema and `stepFields`. Each step validates only its own fields with `validateFields`. The final submit revalidates everything.
- `api.ts` (`submitRequest`) calls the Supabase Edge Function `submit-request` via `supabase.functions.invoke`, with `{ type, name, email, summary, captchaToken }`. Its source is in `supabase/functions/submit-request/index.ts` (Deno): it validates the fields, verifies Turnstile (`TURNSTILE_SECRET_KEY` secret), then inserts into `customer_requests` with the service role key. The browser never writes to the table directly.
- Turnstile tokens are single-use. After a failed submit, the widget is reset (`captchaRef.current.reset()`).
- Env vars are typed in `src/vite-env.d.ts`.
- Emails (Resend, plan in `docs/plan-correos-resend.md`): after saving, `submit-request` sends an acknowledgment to the citizen and a notice to the office mailbox via `supabase/functions/_shared/email.ts` (`sendAndLog`, never throws: a failed email never fails the request; every attempt goes to the `email_log` table). Templates live in `_shared/emails/` (`layout.ts` escapes all user text with `escapeHtml`; the footer always says `notificaciones@oeccbvirtual.app` is only for PQRS and is not a judicial mailbox). Office data used by the functions is repeated in `_shared/office.ts`: keep it in sync with `src/lib/contact.ts` (`NOTIFICATIONS_EMAIL`, `CONTACT_EMAIL`, `OFFICE_NAME`). Secrets: `RESEND_API_KEY`, `EMAIL_FROM`, and `PQRS_OFFICE_NOTICE` (the office notice is sent only when it is `on`; off while the institutional mailbox doesn't receive mail from oeccbvirtual.app). Terms: the last step has a required checkbox (`pqrs/TermsField`) whose link opens `TermsModal` with the text from `pqrs/terms.ts` (approved copy in `docs/terminos-tratamiento-datos.md`; change both together); "Acepto los términos" checks it. `acceptedTerms: z.literal(true)` is part of `requestSchema`; `submit-request` rejects a request without it and stores `customer_requests.terms_accepted_at` (migration `20261007130000_pqrs_terms_accepted.sql`) as proof of the authorization. The acknowledgment email has no reply-to (`notificaciones@` only sends); its footer asks not to reply and links to `/contacto`. The database assigns `customer_requests.request_number` (`PQRS-<year>-<6 digits>`, per-year counter in `request_counters`); `RequestSent` shows it.

## Survey

`/encuesta` loads the active survey (only one can be active; chosen in the dashboard) with `useSurvey()` (`components/survey/useSurvey.ts`), which reads `surveys` + `survey_questions`. Both tables are publicly readable while the survey is active. `SurveyForm` shows one question per step, then a final review step (editable answers + Turnstile). It follows the same pattern as PQRS.
- Question types: `yes_no` → `YesNoQuestion` (boolean) and `scale` → `ScaleQuestion` (number between `scale_min` and `scale_max`), in `survey/questions/`. `QuestionField` picks the component by `question.type`. To add a type: create its component, add it to `QuestionField`, and add its zod schema in `survey/validation.ts` (`answerSchema`).
- Answers are keyed by `question.id`. They are sent to the Edge Function `submit-survey` as `{ surveyId, answers: [{ questionId, value }], captchaToken }` (`survey/api.ts`). The function's source is in `supabase/functions/submit-survey/index.ts` (Deno):
  1. Verifies Turnstile (`TURNSTILE_SECRET_KEY` secret).
  2. Calls the SQL function `public.submit_survey_response(p_survey_id, p_answers)` (`supabase/migrations/20260930120000_submit_survey_response.sql`), which runs as a single transaction. All business rules live there: the survey is active, each question belongs to it, type and range, no duplicates, required questions answered. It raises `survey_not_available`, `invalid_answers` or `missing_required_answers`, which the Edge Function maps to Spanish messages. `survey_answers.value` is a `smallint` from 0 to 10, so `yes_no` is stored as 1 (yes) / 0 (no).
  3. Security: EXECUTE on the function is revoked from `public`/`anon`/`authenticated` and granted only to `service_role`. It is `security invoker` with an empty `search_path`. Don't change it to `security definer`, and don't grant it to `anon`: that would bypass the captcha via `/rest/v1/rpc`.
  Deploy with `supabase functions deploy submit-survey --no-verify-jwt`. JWT verification is off because the client calls it with the publishable key.- Schema: `surveys` and `survey_questions` are publicly readable only when the survey is active. `survey_responses` and `survey_answers` have RLS enabled with no policies, so they are unreadable and unwritable from the client.
- `CaptchaField` (Turnstile) and `CheckIcon` live in `components/ui` and are shared by PQRS and the survey. `CopyButton` (also in `components/ui`) is shared by Contacto and the dashboard Usuarios section.

## Auction notices (Remates)

Plan and decisions in `docs/plan-remates.md`. Schema in `supabase/migrations/20261002120000_create_auction_notices.sql`: `auction_notices` (public read of `is_published` rows only, no write policies yet) and `pdf_folders` (the two number segments of the PDF URL, picked by the notice's `created_at`; no policies). The `auction_notices_before_write` trigger builds `pdf_url` (12-hour `HH`, America/Bogota), keeps `created_at` immutable and sets `updated_at`. It is `security invoker`: whoever writes notices must be able to read `pdf_folders`.
- `/avisos-remates` (`pages/Remates.tsx`) is a read-only list built from `components/remates/`. Filters (`juzgado`, `periodo`, `q`, `pagina`) live in the URL via `useRematesFilters`; `useAuctionNotices` fetches one page server-side (`.range()` + `count: 'exact'`), aborts stale requests and keeps the previous rows while loading. A `PGRST103` (page past the end) sends the user back to page 1.
- Agendado / Realizado and Próximos / Pasados share one rule: a notice is past `REALIZADO_DESPUES_DE_MIN` (60) minutes after `scheduled_at`. The cutoff uses the `now` captured with each request, never `new Date()` during render. Dates are formatted in `America/Bogota`.
- "Ver aviso" in each row opens `RemateDetailModal`, which refetches the notice by id on every opening (`NoticeSelection.openedAt`) and shows a spinner meanwhile. It offers "Ver aviso" (new tab) and "Descargar PDF" via `pdfDownloadUrl()` (`?download=true`, which makes the publications site answer `Content-Disposition: attachment`). The `download` attribute does not work because the PDF is cross-origin without CORS.
- `ui/Pagination` is generic: reuse it for other paginated lists.
- The table is built from shared parts (`remates/tableStyles.ts`, `remates/NoticeCells.tsx`) used by both the public `RematesTable` and the dashboard `AdminRematesTable`; change them there so both stay identical.
- Dashboard management (`src/dashboard/remates/`, `/dashboard/avisos-remates`, plan in `docs/plan-remates-dashboard.md`, migration `20261005180000_auction_notices_admin.sql`): permissions `remates.ver|crear|editar|publicar|eliminar` (per court, via `has_permission('remates.x', court)` in RLS) and `remates.carpetas` (`/dashboard/avisos-remates/carpetas`, `pdf_folders`). RLS works per row, so the `auction_notices_authorize` trigger (named to run before `auction_notices_before_write`) enforces the per-column rules: changing data needs `editar`, changing `is_published` needs `publicar`, and a notice created without `publicar` is hidden; it also fills `created_by` / `updated_by`, and does nothing without a user (SQL Editor, Table Editor). Court-scoped users get their court forced in the filters and the form. The dashboard shows only Publicado / Oculto (`PublicationBadge`), never Agendado / Realizado (that is for the public), and row actions go in an `ActionMenu` (three dots). `dashboard/remates/pdfUrl.ts` repeats the trigger's URL formula for the form preview: change both together. Delete is definitive.

## Hearings (Audiencias, public)

`/audiencias` (`pages/Audiencias.tsx`, components in `components/audiencias/`, phase 2 of `docs/plan-audiencias.md`, migration `20261008170000_public_hearings.sql`) is read-only and mirrors Avisos de Remate: tabs Próximas / Anteriores, court segmented control, type, date range and radicado filters in the URL (`useAudienciasFilters`), server-side pagination. ## Not found page

`pages/NotFound.tsx` (plan in `docs/plan-404.md`) is the catch-all route and also what `pages/Tutorial.tsx` renders for an unknown slug (props `eyebrow`, `title`, `description`, `primaryAction`). It shows the attempted path from `useLocation()`, a primary button ("Ir al inicio" by default), quick links built from `mainLinks`, and `notfound/NotFoundIllustration` ("broken route": the path types itself in a browser bar, a big 404, the site routes with the attempted one marked "No existe" in red). It also adds a `noindex` robots meta while mounted. Netlify must serve the app for every path: `public/_redirects` (`/* /index.html 200`), copied to `dist/` by Vite.

## Decorative illustrations (home, contact, auction notices, PQRS, survey and tutorials)

The home hero (`home/HeroIllustration`, plan in `docs/plan-hero.md`), the contact header (`contacto/ContactIllustration`, plan in `docs/plan-contacto.md`) and the auction notices header (`remates/RematesIllustration`, plan in `docs/plan-remates-ilustracion.md`; hidden below `md` so the table stays on top) and the PQRS header (`pqrs/PqrsIllustration`, plan in `docs/plan-pqrs-ilustracion.md`; also hidden below `md`; tells the form flow and reads type and step names from `pqrs/data.ts`, including `REQUEST_STEPS`, shared with `PqrsForm`) and the survey header (`survey/SurveyIllustration`, plan in `docs/plan-encuesta-ilustracion.md`; also hidden below `md`; one sample answer with small stars from `survey/MiniStars`, never results or averages) and the tutorials header (`tutorials/TutorialsIllustration`, plan in `docs/plan-tutoriales-ilustracion.md`; flat 3:2 canvas based on a Laravel Cloud image, also shown on phones, centered below the title; green citizens on the left as a status color, a fixed card whose title and figures cycle through all the tutorials, 3 s each, and a column of books on the right) show decorative cards, most on a tilted plane. PQRS and survey share the hero pattern: stacked on phones, title + supporting text side by side from `sm` with the button below, illustration from `md`, two columns from `lg`. Shared pieces live in `components/illustration/`: `IllustrationCanvas` (container, scale, tilted plane `matrix(.996,.087,-.174,.985)`, dots and edge masks, `aria-hidden`; `fade="right"` by default, `fade="left"` when a panel leaves through the left edge; `compact` makes the text ≈ 12 % smaller via the `illustration-compact` utility; `flat` removes the tilt, `ratio="3/2"` makes a 512 × 341 canvas and `fade="bottom"` fades only the bottom, used by Tutorials), `IllustrationPanel`, `IllustrationCard` + `IllustrationRow`, `IllustrationMenu`, `StatusDot`, `IllustrationHatch` (striped accent behind a card, color from a token via `--hatch`), `IllustrationButton` (non-focusable fake button), `IllustrationSegmented` (fake segmented control), the Heroicons paths (`illustrationIcons`) and the class strings `enter`, `lift`, `connector`, `connectorCorner`. Each section keeps only its composition and its `data.ts`.
- The canvas is 512 × 400 units. The `illustration-scale` utility (`index.css`) sets `--u` = 1/512 of the nearest `@container` and redefines `--spacing`, text sizes and radii from it, so regular classes (`left-14`, `text-sm`) scale with the width. Inside it, use spacing/text/radius utilities, not fixed px values.
- Animations are `@utility` classes in `index.css`: `animate-illustration-in` (entrance), `-fill` (a bar's width from 0), `-type` (text revealed by animating `max-width` in steps; inline-block + overflow-hidden + nowrap, with a caret after it using `-caret`) and `-cycle` (6 stacked texts taking turns every 3 s in an 18 s loop; only Tutorials uses it, so adjust it together with `tutorials/illustrationData.ts` if the number of tutorials changes). Use them with `motion-safe:`. Each piece sets its delay with `[--illustration-delay:150ms]` (a non-inherited `@property` read inside each `animation` shorthand). Never use `[animation-delay:…]`: the `animation` shorthand of `motion-safe:animate-…` comes later in the CSS and resets it to 0. Never move these animations back to `--animate-*` theme variables: a `var()` inside a theme variable resolves on `:root`. The keyframes animate `transform`; hover lifts use the separate `translate` property. Don't add `inert`: it would disable the hover effects, and nothing inside is focusable.
- Texts come from data (tutorials from `tutorials/data.ts`, contact details from `lib/contact.ts`), never hardcoded.

## Tutorials

`/tutoriales` (`pages/Tutoriales.tsx`) lists the tutorials as cards, and `/tutoriales/:slug` (`pages/Tutorial.tsx`) shows one, with breadcrumb `Inicio › Tutoriales › <title>`, its numbered steps and Anterior / Siguiente links. The detail content uses the full container width. Each step (`TutorialContent`) is a card: from `lg`, text on the left (40 %, vertically centered) and the screenshot on the right (60 %), with the link centered in its own row below; below `lg` they stack (text → image → link). Step screenshots (`TutorialImage`) are capped at 384 px tall (`max-h-96` + `object-contain`, full width) at every size, so portrait captures such as phone screenshots stay centered; the tonal background has padding (vertical `py-3 sm:py-4`, horizontal half of that, `px-1.5 sm:px-2`) so images don't touch its edges; the zoom modal shows them full size. Steps reveal on scroll with `motion-safe:animate-step-reveal` (CSS scroll-driven `animation-timeline: view()` inside `@supports`, so unsupported browsers just show the step). Plan in `docs/plan-tutoriales-pasos.md`. An unknown slug shows a "not found" EmptyState.
- All content lives in `components/tutorials/data.ts` (`tutorials`: `slug`, `title`, `description`, `draft?`, `steps: { title?, text, link?, image? }[]`). `draft: true` shows a "contenido de prueba" notice. Screenshots go in `public/img/tutoriales/<slug>/` and are referenced with `tutorialImage(slug, file)`. `TutorialImage` opens them enlarged in a `Modal`.
- Optional per-tutorial fields: `prerequisites` (slugs → "Antes de empezar" warning with links), `prerequisitesNote`, `intro`, and `next` (slug → "Siguiente paso recomendado" inside the closing "¡Felicidades!" box built from `summary`). Cross-references use slugs, never hardcoded titles or numbers, so titles come from the data.
- These boxes use `Alert` with `live={false}` (static page content must not be a live region) and an SVG `icon`, not emojis. The array order is the display and prev/next order. To add or edit a tutorial, change only the data. Build URLs with `tutorialPath(slug)`, not by hand.
- Nav links use `end` only for `/`, so a section stays highlighted on its subroutes.
- `ScrollToTop` (`components/navigation`), mounted once inside `BrowserRouter` in `App.tsx`, scrolls to the top on every pathname change, so pages don't need their own scroll reset.

Page titles: every page calls `useDocumentMeta({ title })` (`src/lib/useDocumentMeta.ts`), which shows `OECCB Virtual | <title>` in the tab (`SITE_NAME` in `src/lib/contact.ts`) and restores the previous title on unmount. New pages must call it too; `title: null` leaves the title alone.

The office's official name (`OFFICE_NAME`) and contact details (email, address, hours, maps link) are in `src/lib/contact.ts`. Don't repeat them as literals.

The courts (Juzgado 1 and 2) are in `src/lib/courts.ts`, the single source of their names for the whole site: number, short name, official name ("Juzgado 1 Civil del Circuito de Ejecución de Sentencias de Bucaramanga", built with `CONTACT_CITY`) and their despacho code on the Rama Judicial publications portal. `courtPublicationsUrl(despacho)` builds the portal link (verified to open each court's publications); if the portal URL or portlet id changes, fix it only there. Avisos de Remate derives its `COURTS` (`short`, `detail` = name without the short part, `name`) from this file. Exception: tutorial step texts keep the portal's own spelling ("Juzgado 001 de Ejecución Civil del Circuito de Bucaramanga") because users must type it in the portal search. Plan in `docs/plan-footer.md`.

`FooterGlow` (`components/layout`): two layers of diagonal stripes (`glow-stripes-light` in `primary`, `glow-stripes-cover` in the footer background) scroll left with `motion-safe:animate-glow-scroll` at different speeds, blurred at 20 % opacity under a dot pattern, concentrated at the top of the footer and fading downward (`mask-b-from-30% mask-b-to-70%`), `aria-hidden`. Each layer is wider than the footer by one pattern repeat (`--glow-repeat`, 706.16 px) so the loop is seamless at any width. An `IntersectionObserver` pauses it off screen through `--glow-play`, which lives inside the `animation` shorthand (a separate `animation-play-state` class would be reset by it, like `animation-delay`).

Testing note: headless Edge reports `prefers-reduced-motion: reduce` by default, so `motion-safe:` animations don't run there. Use `--force-prefers-no-reduced-motion` or CDP `Emulation.setEmulatedMedia` when checking animations.

Components take a `className` prop that is merged via `cn()` from `src/lib/cn.ts` (clsx + tailwind-merge), so callers can override Tailwind classes. Build new UI from these components before writing raw Tailwind in pages. Because of the `react-refresh/only-export-components` lint rule, keep non-component exports (constants, helpers) in separate `.ts` files, not in `.tsx` component files.

## Dashboard

Private area, all code in `src/dashboard/` (branch `dashboard`; plan and roadmap in `docs/plan-dashboard.md`). `App.tsx` lazy-loads it (`React.lazy(() => import('./dashboard'))` on `/dashboard/*`, `PageLoader` fallback), so the public site doesn't download it; don't import from `src/dashboard` in public code. Same practices as `src/components` (folders with `index.ts` barrels, helpers in `.ts`, `cn()`, tokens), reusing `components/ui` instead of copying.
- `routes.tsx`: `ProtectedRoute` → `ProfileProvider` → `DashboardLayout` wraps every subroute once. Index is `DashboardHome`; each `ready: false` link gets a generated route to `SectionPending`; `*` is `SectionNotFound`.
- `navigation/links.ts` (`dashboardLinks`: `to`, `label`, `description`, `icon`, `group: 'main' | 'admin'`, `ready`, `end?`) is the single source of the sidebar, the Topbar title (`linkForPath`) and the home cards. Menu order: Inicio, Avisos de Remate, Audiencias, PQRS, Encuestas, then Usuarios, Roles, Permisos and Días no hábiles under "Administración". To build a section: create its folder in `src/dashboard/`, add its `<Route>` in `routes.tsx` and set `ready: true`.
- Layout: from `lg`, a sticky 17 rem sidebar (`Sidebar`: `SidebarUser` with initials, name or email, skeleton while loading; `SidebarNav` with `NavLink`s and "Pronto" badges; "Ver sitio público") and on the right a sticky translucent `Topbar` (☰ below `lg`, section `<h1>`, `TopbarActions`: compact `ThemeToggle`, "Mi perfil" button → `/dashboard/perfil`, sign out → `/login` with `replace`), with the page in `<main>` below. Below `lg`, `MobileSidebar` shows the same `Sidebar` in a native `<dialog>` on the left; it closes on navigation, Escape or a click outside.
- `profile/`: `ProfileProvider` loads the profile once; `useProfile()` gives `{ profile, displayName (full_name or email), email, loading, failed, saveFullName }`. A failed query falls back to the email. `saveFullName` updates the menu and greeting without reloading.
- Mi perfil (`/dashboard/perfil`, `pages/ProfilePage`; its link has `group: 'account'`, so it is neither in the menu nor on the home page): `ProfileNameForm` (name, email read-only) and `PasswordForm` (asks for the current password and checks it with `signInWithPassword` before `supabase.auth.updateUser`; Auth error codes mapped to Spanish in `profile/api.ts`), validated with `profile/schema.ts`. Users can update only their own `full_name`: migration `20261005130000_profiles_update_own_name.sql` grants UPDATE on that column only plus an own-row policy, so columns added later (e.g. a role) can't be changed from the browser. Keep it column-scoped; never `grant update on profiles` to `authenticated`. The name rule (letters incl. accents, single space/hyphen/apostrophe/". " separators, 3–120 chars) lives in both `profile/schema.ts` and the `profiles_full_name_format` check constraint (`20261005140000_profiles_full_name_check.sql`); change both together.
- Dashboard pages call `useDocumentMeta({ title, noindex: true })` (titles like `PQRS · Dashboard`).
- **Row and card actions (convention, at every screen size):** every list in the dashboard (tables, cards) puts its per-item actions in `ActionMenu` (three vertical dots), never in loose buttons. Show only the actions the user may do; when an action exists but can't be used right now, keep it with `disabledReason` (shown greyed with the reason) instead of hiding it. Destructive items use `danger`, and every confirmation goes through `ConfirmDialog` (`tone="danger"` to delete, `tone="update"` otherwise). Page-level actions such as "Crear …" stay as regular buttons.
- Access (plan in `docs/plan-usuarios.md`, migration `20261005150000_roles_permissions.sql`): one role per user (`profiles.role_id`); `roles.scope` is `all` (superadmin, oficina: both courts) or `court` (juzgado: only `profiles.court`, 1 or 2, same values as `auction_notices.court`). Permissions are `<module>.<action>` codes in `permissions`, linked in `role_permissions`; `superadmin` (`is_system`) implicitly has all, including future ones. RLS policies must use `public.has_permission('<code>', court)` (always pass the row's court for court data). Each section adds its own permissions in its own migration, together with the policies that check them; never create permissions that nothing checks. `src/dashboard/access/`: `AccessProvider` (inside `ProfileProvider`) loads `get_my_access()`; `useAccess().can(permission, court?)` mirrors `has_permission` for showing/hiding only. Each `dashboardLinks` entry has `permission`; the menu and home filter by it and `RequirePermission` guards the route. No role or inactive → `NoAccess`; `must_change_password` → every route redirects to Mi perfil with the menu disabled until `complete_password_change()`. Protected in the DB: court required by scope, last active superadmin, system roles. `role_id`, `court`, `active` and `must_change_password` are never writable from the browser (the `manage-users` Edge Function writes them).
- PQRS (`src/dashboard/pqrs/`, `/dashboard/pqrs` and `/dashboard/pqrs/:id`, plan in `docs/plan-pqrs-dashboard.md`, migration `20261007140000_pqrs_admin.sql`): permissions `pqrs.ver|gestionar|responder` (not per court: PQRS belong to the office); only the role `director_oficina` (and superadmin) can respond. The browser never writes `customer_requests`: status changes go through `public.set_request_status()` (responded ones never change; closing needs a reason) and the reply through the Edge Function `respond-request` (deploy WITH JWT verification; `respond` saves once, only if still pending, then emails via `requestResponseEmail`; `resend`). The 15-business-day deadline (Mon–Fri from the day after filing, skipping `non_business_days`) is computed only in SQL: `pqrs_due_date()` and the PostgREST computed columns `due_date` / `business_days_left` on `customer_requests`; `pqrs/deadline.ts` only decides how to display them. Home shows pending/overdue counts (`pqrs_summary()`).
- Días no hábiles (`src/dashboard/calendario/`, `/dashboard/dias-no-habiles`, under Administración; plan in `docs/plan-dias-no-habiles.md`, migration `20261007150000_non_business_days.sql`): table `non_business_days` (`day` Mon–Fri only, `kind` festivo | cierre | otro, `reason`). Only `calendario.ver` sees the menu option and page, and `calendario.gestionar` adds, loads a year or deletes; both belong only to superadmin unless granted in Roles. Deadline functions (`is_business_day`, `pqrs_due_date`, `business_days_between`) are `security definer`, so every user gets correct deadlines without reading the table. "Cargar calendario <año>" previews and inserts Colombian national holidays (`calendario/holidays.ts`: fixed, Ley 51 de 1983 moved to Monday, Easter-based) and Rama Judicial days (Holy Mon–Wed, 17 December, judicial vacation 2–10 January and 20–31 December); existing days are skipped.
- Audiencias (`src/dashboard/audiencias/`, `/dashboard/audiencias` and `/dashboard/audiencias/tipos`, plan in `docs/plan-audiencias.md`, migration `20261008150000_hearings.sql`; phase 1 of 4 built): tables `hearings`, `hearing_types` (CRUD with `audiencias.tipos`, only superadmin; `requires_link`, `is_active`), fixed `hearing_statuses` (1 Programada, 2 Realizada, 3 Cancelada) and fixed `execution_courts` (1 and 2, same values as `profiles.court`). Per-court permissions `audiencias.ver|crear|editar|eliminar` (juzgado, oficina, director_oficina). The `hearings_rules` trigger (only with a user, like remates) enforces: new hearings start Programada, in the future, on a business day (`is_business_day`), 7:00–17:00 Bogota in 15-minute steps (`hearing_schedule_error`); Realizada from 1 hour after with `recording_url`; Cancelada from the scheduled time; closed hearings only allow fixing the recording of a Realizada; delete only if future, Programada, without connection link or recording. `data.ts` mirrors these rules for the UI (`canRealizeNow`, `canCancelNow`, `deleteBlocker`): change both together. Views (URL `vista=tabla|semana|mes`, `fecha`): table with tabs Próximas / Por cerrar / Cerradas / Todas, or calendar (`HearingsCalendar`: week grid 7:00–17:00 with 1-hour blocks and lanes for overlaps, month grid, list by day on phones; non-business days striped via `hearing_non_business_days()`). The form warns (doesn't block) when the court has another hearing within the hour; the shared rule check is `audiencias/schedule.ts` (`scheduleProblem`). Avisos de Remate integration (phase 3, migration `20261009120000_hearings_auction_notices.sql`): `hearings.auction_notice_id` (one hearing per notice) and `auction_notice_deleted`; creating a future notice offers "Crear también la audiencia de remate" (only with `audiencias.crear` in that court; disabled with the reason when the date/time breaks the hearing rules) and saves both in one transaction with `create_auction_notice_with_hearing()` (links an existing hearing with the same radicado and time instead of duplicating); the `auction_notices_sync_hearing` triggers move the linked Programada hearing when the notice's radicado, court or date change (hearing rules still apply, so an invalid move rejects the notice edit, and the form blocks it first) and, before a notice is deleted, delete its hearing if deletable or mark it "Aviso de remate eliminado". The notice detail shows the linked hearing and the hearing detail links back to the notice. A hearing whose type requires a link and has none shows "Sin enlace de conexión: no se comunicará". Home card: today and por cerrar.
- Encuestas (`src/dashboard/encuestas/`, `/dashboard/encuestas`, plan in `docs/plan-encuestas-dashboard.md`, migration `20261008120000_surveys_admin.sql`): `encuestas.ver` (oficina, director_oficina; never juzgado) sees the list, the questions (`/:id/preguntas`) and the results (`/:id`); `encuestas.gestionar` (only superadmin unless granted in Roles) creates (`/nueva`), edits (`/:id/editar`), duplicates, activates and deletes. Results come only from `security definer` aggregate functions (`list_surveys`, `survey_stats(p_survey_id, p_from, p_to)` with dates in America/Bogota, `survey_summary` for the Home card: responses this year of the active survey); `survey_responses` / `survey_answers` stay without policies. Period filters (month, month range up to 24 months, year) live in the URL (`usePeriodFilters`, helpers in `period.ts`). Charts are own components in `encuestas/charts/`: `PieChart` (SVG, yes/no) and `BarChart` (scale, one bar per value including zeros), each with "Ver como tabla". "Descargar CSV" (`encuestas/csv.ts`, built in the browser from the loaded counts, no extra permission) exports only the period's totals, one row per option of each question, for Excel in Spanish (`;` separator, UTF-8 BOM, CRLF). Writes go through `save_survey()` (one transaction, `security invoker`): without responses the questions are replaced; with responses the `survey_questions_guard` trigger allows only text changes (title, question text, help, labels), so to change the structure the survey is duplicated. - Usuarios (`src/dashboard/usuarios/`, `/dashboard/usuarios`, `usuarios.ver`; actions need `usuarios.gestionar`): list from `public.list_users()` (migration `20261005160000_list_users.sql`, includes Auth accounts without a profile), filtered client-side; `useUsers` refetches on tab focus, every 60 s while visible and with the "Actualizar" button, since other users' changes don't notify. Row actions (Editar / Asignar rol, Restablecer contraseña, Desactivar / Reactivar) go in an `ActionMenu` at every size; the user's own row only offers "Ir a Mi perfil".

Role codes come from the name (`roleCode`) and never change. Module display names live in `permisos/data.ts` (`MODULE_LABELS`, used by the Roles matrix and the Permisos page): add each new section's module there. `ConfirmDialog` (every confirmation in the dashboard uses it: icon in a tinted circle, a question title such as "¿Eliminar este aviso?", centered text, and two full-width text buttons "Cancelar | <acción>"; `tone="danger"` (red, trash icon) for deleting, `tone="update"` (default, primary) for reversible changes, optional `icon`; focus starts on Cancelar) and `ActionMenu` (three-dots button opening a menu styled like the compact ThemeToggle panel; click to open, closes on choice, outside tap or Escape) are in `src/dashboard/ui/`.

## Design

Visual guidelines are in `design.md`. Key points:
- Colors come from design tokens defined in `@theme` in `src/index.css` (`surface`, `surface-container-*`, `on-surface`, `on-surface-variant`, `outline-variant`, `primary`, `primary-dim`, `on-primary`, `primary-container`). They map to Tailwind's `slate` and `blue`. Use the token classes (`bg-surface-container-low`, `text-on-surface`, `border-outline-variant/15`). Don't use raw palette colors or `dark:`: the tokens are redefined for dark mode. That is also why they use `@theme` and not `@theme inline`. The only exception is status colors (green/amber/red, which do use `dark:`).
- No solid 1px borders for sectioning. Separate areas with background shifts. Elevation comes from layered surfaces, and `shadow-ambient` is used only for floating elements.
- Favicon: the list icon (Material "vertical split") from the previous Tutoriales site, in the `primary` color. The SVG can't read the CSS tokens, so the hex values are hardcoded: `#193cb8` (blue-800) and, under `prefers-color-scheme: dark`, `#51a2ff` (blue-400). If `primary` changes, update them. `public/favicon.svg` plus PNG fallbacks `favicon-32.png` and `apple-touch-icon.png` (180 px, white background), linked in `index.html` (`?v=` busts the old cached icon). If you change the SVG, regenerate the PNGs (light color only).
- Fonts: Inter (`font-sans`, the default) and Manrope (`font-display`, applied to `h1`–`h3` in base styles), loaded from Google Fonts in `index.html`.
- Theme (light / dark / system): `ThemeProvider` (`src/context/ThemeContext.tsx`, hook `useTheme` in `src/context/theme.ts`) writes `data-theme="light|dark"` on `<html>` and saves the choice in `localStorage` (`theme` key). "System" removes the attribute. `src/index.css` defines a custom `dark` variant that is active with `data-theme="dark"`, or with `prefers-color-scheme: dark` when there is no `data-theme`. The dark tokens use that same variant (`:root { @variant dark { … } }`). An inline script in `index.html` applies the saved theme before React renders to avoid a flash. If you change the storage key, update both places. The control is `ThemeToggle` (`components/ui`): `variant="compact"` in the desktop Header (only the current theme's icon; the 3 options open in a dropdown on hover or focus-within, Escape closes it, a mouse click releases focus so it closes) and the default segmented variant with labels in MobileMenu (its `onSelect` closes the menu). The mobile menu also closes on a click or tap outside the header and with Escape (listeners in `Header`). Next to it, the desktop sign-in link is an icon-only `ButtonLink size="icon"` with `aria-label` and a `Tooltip` ("Iniciar sesión" or "Ir al dashboard"). Plan in `docs/plan-navegacion.md`.
